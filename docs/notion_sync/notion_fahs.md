# فحص


# الهدف

تنفيذ مراجعة واختبار عملي شامل لمشروع مدرسة العمرابي الحالي، باستخدام بيانات اختبار اصطناعية واقعية، مع إثبات سلوك الموقع وقاعدة البيانات وتطبيق أولياء الأمور. المطلوب تنفيذ فعلي على المستودع والبيئة السحابية المتصلين، لا الاكتفاء بقراءة الكود أو كتابة خطة.


# تعليمات التشغيل

أنت وكيل تنفيذ مجهول الاسم يعمل من خلال بيئة Google Antigravity المتصلة بمستودع GitHub الخاص بمشروع العمرابي. لا تفترض أنك Gemini أو أي نموذج آخر، ولا تذكر هوية نموذج. وجّه كل خطوة إلى مشروع العمرابي الحالي ومستودعه وقاعدة Supabase المرتبطة به.

استخدم إمكانات التشغيل السحابية المتاحة لديك لتشغيل المتصفح والاختبارات على خادم بعيد. لا تعتمد على موارد جهاز المستخدم المحلي الضعيف (Core i3، الجيل الرابع، دون بطاقة رسومية منفصلة). إذا كانت أداة أو صلاحية غير متاحة، اذكر ذلك صراحة ولا تدّع تنفيذها.


# القرارات والنطاق المعتمد

* العمل على المشروع الحالي نفسه: مستودع GitHub المتصل بـ Antigravity، وتطبيقه، وقاعدة Supabase المرتبطة به. لا تنشئ مشروعاً جانبياً أو قاعدة Supabase جديدة دون طلب.
* المطلوب إنشاء مجموعة بيانات اختبار جديدة تقارب 200 طالب، موزعة على جميع المراحل التي طلبها المالك: الروضة، الابتدائي، الأساس، والثانوي.
* جميع البيانات الجديدة اصطناعية بالكامل لكنها واقعية ومتسقة داخلياً؛ لا تستخدم بيانات أشخاص حقيقيين ولا أرقاماً عشوائية غير مترابطة.
* المطلوب فحص الموقع الإداري وتطبيق Android لأولياء الأمور وقاعدة البيانات باعتبارها منظومة واحدة.
* المطلوب أن ينفذ الوكيل الاختبارات بنفسه عبر متصفح آلي مثل Playwright، وأدوات فحص المتصفح مثل Chrome DevTools MCP عند توفرها، واختبارات قاعدة البيانات مثل pgTAP، واختبار Android عبر Appium أو خدمة أجهزة سحابية عند توفرها.
* لا تعتبر كتابة الاختبار أو نجاح البناء وحدهما دليلاً على أن الوظيفة تعمل.

# شرط حاسم قبل حذف البيانات

المالك صرّح بأن البيانات الموجودة حالياً تجريبية وغير مهمة، وطلب استبدالها ببيانات اختبار جديدة. هذا تفويض لتنظيف بيانات الاختبار فقط، وليس تفويضاً لحذف مخطط قاعدة البيانات أو ترحيلاتها أو إعدادات المشروع أو الأسرار أو سجلات التدقيق الضرورية.

قبل الحذف:

1. افحص اتصال Supabase الفعلي وهوية المشروع والبيئة المرتبطة بالتطبيق، وتأكد أنك لا تستهدف قاعدة إنتاج أو مشروعاً غير مقصود.
1. افحص الجداول والعلاقات والقيود والمفاتيح الأجنبية وRLS والدوال والمشغلات، وحدد بدقة كل الجداول التي تحتوي بيانات اختبار.
1. افحص إن كانت هناك بيانات أو حسابات أو سجلات لا يمكن إثبات أنها تجريبية. لا تحذف أي عنصر ملتبس؛ أوقف الحذف لذلك الجزء واشرحه.
1. اعرض قائمة موجزة بالجداول ونطاق الحذف المتوقع قبل تنفيذ الحذف، واطلب تأكيداً من المالك إذا لم تكن هوية قاعدة البيانات أو طبيعة البيانات محسومة.
1. لا تحذف الجداول أو الأعمدة أو السياسات أو الدوال أو الترحيلات. لا تستخدم DROP SCHEMA أو reset شامل للمخطط.
1. احذف سجلات البيانات التجريبية القديمة التابعة للاختبارات فقط، مع احترام ترتيب العلاقات والمفاتيح الأجنبية، ولا تمسح سجل التدقيق أو سجلات الأمن التي يحتاجها التحقيق.
1. سجّل ما حُذف وعدد السجلات لكل جدول. لا تكتب أن التنظيف اكتمل دون نتيجة SQL فعلية.

# المرحلة الأولى: تدقيق الحالة الحالية قبل التعديل

افحص آخر commit في main وحالة المستودع وجميع التغييرات غير المدمجة، ثم:

* راجع ملفات التطبيق والواجهات والخدمات وواجهات API والمصادقة والصلاحيات والاختبارات.
* راجع كل ملفات Supabase migrations بالترتيب، وملف journal إن وجد، وقارنها بالمخطط الحي وسجل الترحيلات المطبقة.
* لا تطبق أي migration تلقائياً. حلل كل ترحيل، خاصة 0009 و0011 و0012 وأي ترحيلات لاحقة، وحدد التغييرات الخطرة أو المتعارضة.
* أعد فحص مشكلة parent_app_login وparent_get_portal_data وtemp_password_code وصلاحيات anon وauthenticated وRLS. لا تفترض أن تقرير Claude صحيح أو خاطئ قبل قراءة SQL الفعلي واختبار المسارات.
* افحص الاختبارات الحالية: هل تستورد منطق التطبيق الحقيقي أم تعيد كتابة المنطق داخل الاختبار؟ استبدل الاختبارات الوهمية باختبارات فعلية عند الإمكان.
* شغّل tsc --noEmit، lint، build، واختبارات المشروع المتاحة، وسجّل النتائج الفعلية.
* افحص أسرار المستودع وتاريخه دون طباعة الأسرار في التقارير. إذا ظهر سر حقيقي مكشوف، حدّد نوعه ومكانه دون إعادة عرضه، واطلب تدويره.
* طابق التنفيذ مع قرارات Notion ذات الصلة، خاصة «إصلاح الأخطاء» و«plan1» ومتطلبات النظام و«تطبيق العمرابي». عند التعارض، اذكره ولا تخترع قراراً جديداً. لا تعتبر دور المحاسب أو أي مرحلة أو وظيفة جديدة معتمدة لمجرد وجودها في الكود.

# المرحلة الثانية: إصلاح المشاكل الفعلية

رتّب النتائج حسب الخطورة: حرج، عالٍ، متوسط، منخفض. لكل مشكلة:

* خطوات إعادة الإنتاج والدليل.
* السبب الجذري مع تصنيف: مؤكد، مرجح، غير محسوم.
* الملفات والجداول والدوال والسياسات المتأثرة.
* أصغر إصلاح آمن.
* اختبارات تثبت الإصلاح.
أولوية قصوى لأمن حسابات أولياء الأمور:

* لا تمنح anon وصولاً إلى بيانات الأسر أو الطلاب.
* لا تعتمد على رقم الحساب أو المعرّف وحده كوسيلة مصادقة.
* استخدم جلسة موثقة ومصادقة حقيقية، وتحقق خادمياً من ربط ولي الأمر بأبنائه.
* اختبر حسابين مختلفين ومحاولات الوصول المتبادل وتعديل المعرفات وانتهاء الجلسة والحساب غير المعتمد.
* لا تكتفِ بإزالة GRANT؛ راجع جسم الدوال وRLS وSECURITY DEFINER وsearch_path وكل مسارات الوصول.
لا تعدّل بيانات الدرجات أو الحضور أو الرسوم أو المدفوعات أو الإعفاءات أو العلاقات الحقيقية. لا تنشر ولا تدمج إلى main ولا تطبق ترحيلات على الإنتاج دون موافقة صريحة بعد عرض الأثر. استخدم فرعاً منفصلاً وPull Request عند توفر الصلاحيات.


# المرحلة الثالثة: إنشاء بيانات اختبار واقعية لنحو 200 طالب

بعد فحص المخطط الفعلي وإصلاح ما يمنع الإدخال الآمن، أنشئ بيانات اصطناعية مترابطة في قاعدة المشروع الحالية. لا تخترع أعمدة أو جداول؛ استعمل المخطط الفعلي، واذكر أي نقص في النموذج.

يجب أن تغطي البيانات:

* الروضة والابتدائي والأساس والثانوي، مع توزيع معقول يراعي الصفوف والشعب التي يدعمها النظام فعلياً.
* طلاب مستجدين ومنقولين وحاليين، وحالات الانسحاب والإعادة والتخرج فقط حيث يسمح بها الصف والقواعد.
* أسماء عربية متنوعة واقعية، تواريخ ميلاد منطقية، أرقام اتصال اختبارية غير مملوكة لأشخاص حقيقيين، وعناوين عامة اصطناعية عند الحاجة.
* أولياء أمور متعددين، وبعض الأسر لديها أكثر من ابن، مع روابط صحيحة وفريدة بين كل ولي أمر وأبنائه.
* رقم مدرسي فريد وثابت لكل طالب وفق آلية النظام.
* معرّف/رقم حساب مستقل وفريد لكل ولي أمر، لا يُشتق من رقم الطالب ولا يُستخدم وحده للمصادقة.
* حسابات أولياء أمور بحالات مختلفة: غير مفعل، بانتظار الاعتماد، مفعل، موقوف، مع اختبار صلاحيات كل حالة.
* رسوم دراسية وفئات إضافية وأقساط ومدفوعات كاملة وجزئية وإعفاءات ومنح، دون تناقض حسابي.
* درجات وامتحانات وفترات ونتائج بحالات مسودة ومعتمدة ومنشورة، وفق قواعد النظام.
* حضور لأيام وصفوف وشعب مختلفة: حاضر، غائب بعذر، غائب دون عذر، متأخر، ويوم لم يسجل فيه الحضور أصلاً.
* بيانات تكشف الحالات الحدية: نقص حقل اختياري، تكرار إدخال، ولي أمر متعدد الأبناء، طالب منقول، صف بلا شعبة إن كان مسموحاً، بيانات فارغة، تعارض صلاحيات، اتصال متقطع، وإعادة محاولة.
لا تستخدم أسماء أو أرقاماً أو معلومات شخصية حقيقية. أنشئ ملف seed قابل لإعادة التشغيل بأمان (idempotent) أو آلية تمنع التكرار، ووثّق طريقة التنظيف وإعادة التعبئة.


# المرحلة الرابعة: اختبار الموقع كأنك مستخدم حقيقي

استخدم Playwright على خادم سحابي بعيد إن أمكن. أنشئ اختبارات E2E تغطي:

* تسجيل الدخول والخروج واستعادة الجلسة.
* لوحة المدير والتنقل بين الصفحات وحالات التحميل والفراغ والخطأ.
* إنشاء طالب وتعديله وربطه بولي الأمر.
* قواعد المستجد والمنقول والصف والشعبة.
* إدارة المراحل والصفوف والشعب والسنوات الدراسية.
* الحضور، وعدم اعتبار اليوم حاضراً تلقائياً إذا لم تُنشأ جلسة حضور.
* الرسوم والأقساط والمدفوعات والإعفاءات.
* إدخال الدرجات واعتمادها ونشرها.
* الترحيل السنوي والترقية والإعادة والتخرج والتحويل، مع منع الحالات غير المنطقية.
* التقارير والطباعة والتصدير إن كانت موجودة.
* صفحات الإعدادات والمستخدمين والصلاحيات وسجل التدقيق.
* الشاشات التي تظهر حالياً «لا توجد بيانات»؛ تحقق هل هي حالة فارغة صحيحة أم فشل جلب أو ربط بيانات.
التقط لقطات شاشة وسجلات Console وNetwork عند الفشل، مع تنقيح أي بيانات شخصية أو أسرار. تحقق من النتيجة في قاعدة البيانات بعد عمليات الحفظ، وليس من رسالة الواجهة فقط.


# المرحلة الخامسة: اختبار تطبيق أولياء الأمور والربط

* تحقق من وجود تطبيق Android الفعلي وإمكان بنائه وتشغيله. لا تعتبر صفحة ويب أو WebView بديلاً تلقائياً عن APK حقيقي.
* اختبر تسجيل الدخول بحساب ولي الأمر المعتمد، وربط عدة أبناء، والتبديل بينهم، وعرض الحضور والنتائج المنشورة والرسوم والإعلانات.
* اختبر منع الحساب غير المعتمد والموقوف، ومنع ولي الأمر من الوصول إلى أبناء غير مرتبطين به حتى عبر API مباشرة.
* اختبر إشعار الغياب وتجنب إرسال بيانات حساسة في الإشعار، واختبر تأخر الإشعار وتكراره ورفض الإذن.
* قارن ما يظهر في التطبيق بما هو محفوظ ومعتمد في قاعدة البيانات.
* اختبر فشل الشبكة والعودة والتحميل وحالات البيانات غير المنشورة.
* إذا تعذر تشغيل Android على جهاز سحابي، اذكر الأداة المطلوبة والجزء الذي لم يُختبر؛ لا تدّع اختبار APK.

# المرحلة السادسة: بيئة التنفيذ السحابية

أولوية التشغيل على موارد بعيدة لا على حاسوب المالك:

* افحص إمكانية استخدام GitHub Actions المستضاف لتشغيل CI وPlaywright.
* استخدم Playwright browsers على runner سحابي، واحفظ تقارير HTML ولقطات الشاشة وtrace artifacts.
* شغّل اختبارات قاعدة البيانات في بيئة اختبار مناسبة وبصلاحيات محدودة.
* افحص إمكانية Appium أو خدمة أجهزة Android سحابية لاختبارات APK.
* لا تضع مفاتيح Supabase السرية أو كلمات المرور في GitHub أو ملفات السجل. استخدم GitHub Secrets/بيئة أسرار مناسبة وبأقل صلاحية.
* لا تستهلك موارد أو أرصدة مدفوعة دون معرفة التكلفة أو موافقة المالك.
* لا تدّع أن Antigravity يشغّل متصفحاً سحابياً تلقائياً ما لم تتحقق من إعداد الأداة الفعلي. GitHub Actions يشغّل الاختبارات، لكنه لا يمنح النموذج وحده قدرة التحكم التفاعلي إلا إذا بنيت وربطت سير العمل المناسب.

# قواعد الأمان وعدم الإتلاف

* لا تلمس الإنتاج أو تنشر أو تدمج أو تطبق migrations أو تحذف بيانات ملتبسة دون موافقة واضحة.
* لا تكشف الأسرار أو بيانات الطلاب في التقارير أو artifacts العامة.
* لا تجعل بيانات الاختبار متاحة في واجهة الإنتاج أو تطبيق المستخدمين الحقيقيين.
* لا تستخدم مفاتيح service_role في المتصفح أو APK.
* لا تضع كلمات مرور اختبارية حقيقية أو قابلة لإعادة الاستخدام خارج بيئة الاختبار.
* افصل بوضوح بين حذف بيانات الاختبار، وتغيير مخطط القاعدة، وتطبيق migrations؛ هذه عمليات مختلفة.
* إذا ظهر أن المشروع الحالي هو إنتاج فعلي أو يحتوي بيانات غير تجريبية، أوقف الحذف فوراً واطلب قرار المالك.

# شكل التقرير النهائي

قدّم تقريراً واحداً واضحاً بالعربية يتضمن:

1. البيئة التي فُحصت: commit، فرع Git، مشروع Supabase المستهدف، وأدوات التشغيل.
1. ما تم فحصه فعلياً وما تعذر الوصول إليه.
1. الجداول والبيانات التي حُذفت وأعداد السجلات، إن نُفذ الحذف.
1. عدد الطلاب وأولياء الأمور والعلاقات التي أُنشئت، مع توزيع المراحل.
1. قائمة المشاكل المؤكدة والمحتملة وغير المحسومة، مع أدلة وروابط ملفات أو اختبارات.
1. الترحيلات الآمنة وغير الآمنة وسبب التصنيف، دون تطبيق غير معتمد.
1. نتائج كل اختبار: الاسم، المتوقع، الفعلي، ناجح/فاشل/لم يُشغّل.
1. أخطاء الصفحات والربط والتطبيق، مع لقطات وتقارير منقحة.
1. التغييرات البرمجية التي أُجريت في الفرع المنفصل، وما لم يُعدّل.
1. المخاطر المتبقية والقرارات المطلوبة من المالك.

# قاعدة النجاح

لا تقل «اكتمل» أو «تم الإصلاح» لمجرد أن الكود عُدّل أو البناء نجح. لا تُغلق مشكلة إلا بدليل قابل لإعادة التشغيل يثبت السلوك المطلوب. افصل دائماً بين ما نُفذ، وما اختُبر، وما نجح، وما فشل، وما تعذر التحقق منه.
