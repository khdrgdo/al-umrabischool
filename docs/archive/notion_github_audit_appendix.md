# ملحق تدقيق GitHub — مطابقة المصدر ومخاطر إضافية

تم فحص مستودع GitHub الذي أرسله المستخدم: khdrgdo/al-umrabischool، الفرع الافتراضي main، عند commit 8e4bffa0cb7b6765e37075cc38fa548424841172 بتاريخ 2026-10-22. هذا الفحص الإضافي يؤكد الوصول إلى المستودع العام ويبدأ مطابقة نتائج Lovable مع GitHub. لم تُشغّل الشفرة أو الاختبارات في بيئة محلية، ولم يُفحص إعداد Supabase الإنتاجي.


## تحديث مهم لحالة المصدر

* GitHub وLovable يظهران commit الحالي نفسه 8e4bffa0cb7b6765e37075cc38fa548424841172؛ هذا يثبت توافق الرأس في وقت الفحص، لا يثبت أن قاعدة البيانات المنشورة مطابقة للمigrations.
* المستودع يحوي ملفًا باسم .env متعقبًا في Git. الفحص الآمن لمحتواه أظهر متغيرات مشروع Supabase وعناوينه ومفتاحًا من نوع publishable فقط، ولم تُنسخ القيم السرية إلى هذا التقرير. مفتاح Supabase publishable مخصص للاستخدام العام عادةً وليس كافيًا وحده لتجاوز RLS، لذا لا أصف هذا وحده بأنه تسريب مفتاح إداري. لكن تخزين إعدادات البيئة في ملف متعقب ممارسة غير لازمة؛ انقلها إلى إعدادات البيئة، واحتفظ بقالب .env.example بقيم وهمية، وتحقق من كامل تاريخ Git أن أي service-role/secret لم يُنشر سابقًا. إذا ظهر أي سر حقيقي في التاريخ، دوّره فورًا ولا تكتفِ بحذف الملف في commit جديد.
* .gitignore الحالي لا يتضمن .env، لذلك قد يُعاد تتبعه مستقبلًا حتى بعد حذفه من الفهرس إن لم يُصلح ذلك.

## Findings إضافية مؤكدة من ملفات GitHub


### GH-001 — ملف .env متعقب وغير مستثنى من Git

الأولوية: P2، وترتفع إلى P0 إذا احتوى التاريخ على مفتاح سري حقيقي.
الدليل: ملف .env موجود في جذر المستودع، و.gitignore لا يتضمن .env. المتغيرات الحالية التي روجعت هي IDs/URLs ومفتاح publishable.
الإصلاح: أضف .env وملفات البيئة المحلية إلى .gitignore، أبقِ .env.example دون قيم حقيقية، أزل الملف من التتبع بـ git rm --cached .env في تغيير منفصل، وافحص تاريخ المستودع ونتائج secret scanning قبل اعتماد الإغلاق. لا تعِد كتابة التاريخ المنشور المتصل بـ Lovable دون خطة متفق عليها.
الاختبار: تأكد أن git status --ignored يظهر ملف البيئة مستثنى، وأن الفحص التاريخي لا يجد أسرارًا حقيقية.


### GH-002 — بيانات تجريبية وحسابات اختبار موثقة ضمن حالة المشروع

الأولوية: P1 قبل الإنتاج.
الدليل: docs/PROJECT_STATUS.md يذكر حسابات .test وبيانات طلاب DEMO- ويقول إنها للاختبار ويجب حذفها قبل التشغيل الحقيقي.
الخطر: إذا وصلت بيانات الاختبار إلى قاعدة إنتاج أو بقيت حسابات تجريبية نشطة، قد تختلط التقارير أو توجد حسابات معروفة/غير ملائمة للإنتاج.
الإصلاح: لا تحذف شيئًا مباشرةً. افحص قاعدة الإنتاج الفعلية وقاعدة التطوير كلًا على حدة؛ أنشئ تقريرًا يحدد حسابات .test والطلاب DEMO-، ثم احصل على موافقة قبل تعطيل الحسابات أو أرشفة/حذف بيانات الاختبار. اجعل seed خاصًا ببيئة الاختبار ولا يُشغّل في الإنتاج.
الاختبار: فحص قاعدة الإنتاج لا يجد سجلات اختبار بعد إجراء معتمد؛ إعادة تهيئة staging تنتج بيانات اختبار معزولة فقط.


### GH-003 — التوثيق متأخر عن الكود في حالة بعض الوحدات

الأولوية: P2، خطر استمرارية وتوجيه النموذج.
الدليل: docs/PROJECT_STATUS.md ما زالت تصف الحضور والدرجات والمالية والترحيل كميزات لم تُنفذ، مع أن المستودع يحتوي migrations وصفحات لهذه الوحدات. هذا لا يثبت أنها مكتملة؛ لكنه يثبت أن وصف الحالة غير كافٍ/قديم.
الإصلاح: تحديث الحالة بناءً على الاختبار: «ملف موجود»، «تطبيق مبدئي»، «اختبار آلي ناجح»، «اختبار staging»، «جاهز للإنتاج». لا تستخدم «يعمل» لمجرد وجود ملف أو migration.


### GH-004 — الاختبارات المسجلة لا تثبت سلامة التكامل أو RLS

الأولوية: P1 قبل الإنتاج.
الدليل: package.json يعرّف test وlint وbuild، وdocs/PROJECT_STATUS.md يقر بأن سياسات RLS لم تُختبر آليًا، عدا اختبار وحدة للصلاحيات. وجود أوامر الاختبار لا يعني أنها نجحت.
الإصلاح: تشغيل lint/typecheck/tests/build في بيئة معزولة وتسجيل النتائج، ثم إضافة اختبارات تكامل ضد PostgreSQL/Supabase staging تغطي كل دور وRLS وRPCs والمعاملات. لا تضع بيانات أو أسرار الإنتاج في CI.
