# مواصفة حساب ولي الأمر ورقم الحساب وOTP
**الحالة:** قرار منتج معتمد، مواصفة تنفيذ أولية — لا تطبق على قاعدة حية قبل مراجعة منفصلة
**التاريخ:** 2026-11-07

## 1. القرارات الملزمة الأحدث
1. ينشئ النظام لكل ولي أمر رقم حساب داخلياً فريداً وثابتاً. الرقم ليس رقم الهاتف ولا الرقم المدرسي لأي طالب.
2. الدخول برقم ولي الأمر وكلمة مرور.
3. استعادة كلمة المرور عبر OTP يطلبه ولي الأمر ويرسل إلى وسيلة اتصال موثقة.
4. حساب واحد لولي الأمر مهما تعدد أبناؤه أو اختلفت مدارسهم ومراحلهم.
5. يجب أن يدعم النموذج ارتباط الطالب بأكثر من ولي أمر، مع علاقة وصلاحيات مستقلة لكل رابط.
6. لا تسجيل ذاتي مفتوح. تنشئ الإدارة الحساب وتتحقق من الهوية والعلاقة وتفعّل الربط.
7. لا تكشف واجهات الدخول أو الاستعادة وجود الحساب أو أسماء الأبناء.
8. لا كلمات مرور أو OTP بنص صريح في قاعدة البيانات أو السجلات.
9. التفويض في الخادم وRLS؛ لا يعتمد على إخفاء عناصر الواجهة.
10. فك الارتباط لا يحذف الطلاب أو التاريخ الأكاديمي؛ بل يسجل حالة الرابط وتاريخه وسببه.

## 2. التوافق مع التصميم السابق
- يبقى Supabase Auth مسؤولاً عن كلمات المرور والجلسات؛ لا تنشأ آلية كلمات مرور مخصصة.
- رمز التفعيل الإداري الحالي منفصل عن OTP الخاص باستعادة كلمة المرور.
- المرجع APP-2 السابق يشترط معرّف دخول عشوائياً غير متسلسل، ويجعل إعادة التعيين إجراءً إدارياً حضورياً. القرار الأحدث يغير الاستعادة إلى OTP ذاتي ويطلب رقماً داخلياً. يجب تحديث APP-2 صراحة قبل اعتباره مرجعاً تنفيذياً نهائياً.
- توصية أمنية: إذا كان المقصود رقماً رقمياً فقط، فليكن عشوائياً غير متسلسل، لا رقمًا متزايداً. لا تعتمد صيغة أو طولاً نهائياً قبل اختبار منع التخمين ومعدل المحاولات. الرقم ليس كلمة مرور ولا عامل مصادقة.
- لا يوجد في الملفات التي تمت مراجعتها ما يثبت تهيئة مزود SMS فعلي. لا يُعلن OTP الهاتفي جاهزاً قبل اختيار المزود وربطه واختبار التسليم والتكلفة.

## 3. الموجود حالياً الذي يجب إعادة استخدامه أو مراجعته
- جدول guardians موجود وفيه account_code وuser_id وstatus بحسب الترحيلات.
- جدول guardian_students موجود بالفعل ويمثل علاقة ربط ولي الأمر بالطالب؛ لا تنشئ جدولاً مكرراً.
- يوجد guardian_activation_codes ومسار تفعيل إداري في الخادم. لا تخلط رمز التفعيل الإداري مع OTP ذاتي الاستعادة.
- الترحيل 20261027000013_parent_auth_activation_and_owner_bootstrap.sql يحتوي مسار Supabase Auth ورموزاً إدارية أحادية الاستخدام. راجع أثره وسجل تطبيقه في بيئة التطوير قبل أي تعديل.
- guardians.school_id إلزامي في الترحيل الأولي، وهذا لا يلائم ولي أمر لأبناء في مدارس مختلفة. افحص هل يجب اشتقاق المدارس من الأبناء أم إنشاء علاقة مستقلة؛ لا تغير القيد قبل مراجعة نموذج المؤسسة.
- حالة قاعدة الإنتاج وسجل الترحيلات الحي غير مثبتين هنا. لا تفترض أن أي ترحيل في Git مطبق على الإنتاج.

## 4. نموذج البيانات المستهدف — تصميم وليس SQL تنفيذي

### guardians
هوية داخلية ثابتة، رقم حساب فريد يولده الخادم بمصدر عشوائي آمن وغير متسلسل، user_id فريد يشير إلى Supabase Auth، الاسم ووسائل الاتصال، حقول إثبات ملكية وسيلة الاتصال، حالة الحساب وتاريخ/منفذ تغييرها. لا تضع كلمة المرور أو OTP في هذا الجدول.

### guardian_students
أعد استخدام الجدول الحالي وتطويره عند الحاجة: guardian_id وstudent_id، نوع العلاقة، حالة الربط pending/verified/revoked، verified_by وverified_at وrevoked_by وrevoked_at وسبب فك الربط، وصلاحيات محددة لكل رابط عند اعتمادها. فك الربط تحديث حالة موثق، لا حذف تاريخي.

### OTP للاستعادة
جدول داخلي لا يصل إليه anon أو authenticated مباشرة، ويحتوي مرجع ولي الأمر والغرض، تجزئة الرمز، وقت الإصدار والانتهاء، عدد المحاولات ووقت الاستهلاك. التحقق والاستهلاك عبر وظيفة خادم محمية فقط. الرمز قصير العمر وأحادي الاستخدام. لا تعتمد على ذاكرة نسخة الخادم وحدها لتحديد المعدل.

### تعدد المدارس
لا تجعل school_id على guardians قيداً يفرض مدرسة واحدة على ولي الأمر. افحص هل علاقة المدرسة مشتقة من الطلاب؛ لا تضف guardian_schools إلا إذا كان لها معنى تشغيلي مستقل.

## 5. عقد API المقترح
| العملية | الجهة | المدخلات | القواعد |
|---|---|---|---|
| إنشاء حساب ولي أمر | إدارة موثقة | الاسم ووسيلة الاتصال | رقم داخلي فريد؛ لا تسجيل عام |
| ربط طالب | إدارة موثقة | guardian_id, student_id, relation, permissions | تحقق من الصلاحية وسجل تدقيق |
| إصدار رمز التفعيل | إدارة | guardian_id | يعرض مرة واحدة ولا يخزن نصاً |
| إكمال التفعيل | Android → خدمة خادم | account_code, activation_code, password | تحقق ثم إنشاء/ربط Supabase Auth |
| تسجيل الدخول | Android → Auth/خدمة وسيطة | account_code, password | تحويل الرقم إلى هوية Auth داخلياً |
| طلب OTP | Android → خدمة خادم | account_code | رد موحد سواء وجد الحساب أم لا |
| تأكيد OTP وتعيين كلمة مرور | Android → خدمة خادم | account_code, otp, new_password | تحقق أحادي الاستخدام وإبطال الجلسات القديمة |
| عرض الأبناء | Android → RPC محمية | جلسة مصادق عليها | الأبناء الموثقون فقط |
| تبديل الطالب | Android | student_id | كل طلب خادمي يتحقق من الرابط |
| إيقاف الحساب | إدارة | guardian_id, reason | تغيير حالة وإبطال جلسات وسجل تدقيق |

ردود طلب OTP عامة وثابتة ولا تؤكد وجود الحساب. لا ترسل OTP إلى هاتف غير موثق. لا تعرض التطبيق أرقام الاتصال كاملة إلا عند الحاجة وبشكل مقنّع.

## 6. متطلبات الأمن
- RLS تمنع ولي الأمر من قراءة جداول الطلاب أو روابط أولياء الأمور مباشرة دون حاجة وصلاحية محددة.
- كل SECURITY DEFINER له search_path ثابت، وتسحب صلاحيات PUBLIC وanon، وتمنح الصلاحية الضرورية فقط.
- كل قراءة طالب تتحقق خادمياً من المستخدم المصادق عليه، وحساب ولي الأمر الفعال، ورابط الطالب الموثق وغير الملغى، وحالة نشر البيانات.
- منع تعداد الحسابات برسائل عامة ومعدل مركزي يستمر عبر جميع نسخ الخادم.
- OTP قصير العمر، أحادي الاستخدام، حد محاولات، وإبطال الرمز السابق عند إصدار جديد، وعدم تسجيل الرمز.
- إبطال refresh sessions عند تغيير كلمة المرور أو إيقاف الحساب؛ اختبر السلوك الفعلي مع Supabase Auth.
- لا تضع service_role أو أسرار SMS في APK أو مستودع Git.
- كل إنشاء/تفعيل/ربط/فك ربط/إيقاف/إعادة تعيين يسجل في audit log.
- لا تستخدم ON DELETE CASCADE بطريقة تمحو سجل علاقة الطالب بولي الأمر أو التاريخ الأكاديمي.

## 7. خطة التنفيذ
1. مراجعة المخطط الحالي ومقارنته بالترحيلات وسجل staging. لا تستنتج أن Git يساوي قاعدة الإنتاج.
2. تحديث APP-2 لتوثيق التغيير من إعادة تعيين حضورية فقط إلى OTP ذاتي، بعد اختيار قناة الإرسال.
3. اختيار قناة OTP: مزود SMS موثق، أو بريد حقيقي موثق، أو الإبقاء مؤقتاً على الاستعادة الإدارية حتى تهيئة مزود. لا تنفذ إرسالاً وهمياً.
4. تطوير قاعدة البيانات على staging فقط بترحيلات جديدة قابلة للمراجعة؛ لا تعدّل ترحيلاً سبق تطبيقه.
5. اختبارات PostgreSQL/RLS: أسرتان، ولي متعدد الأبناء، طالب متعدد الأولياء، روابط ملغاة، حساب موقوف، محاولات OTP.
6. اختبارات Auth الفعلية: تفعيل ودخول وطلب OTP وتأكيده وتغيير كلمة المرور وإبطال الجلسات.
7. Android: إدخال رقم الحساب، كلمة المرور، استعادة OTP، حالات الخطأ، اختيار الأبناء، وتبديل الطالب.
8. اختبار APK على جهاز فعلي قبل وصفه بأنه جاهز.

## 8. اختبارات قبول إلزامية
- ولي A لا يقرأ بيانات ولي B حتى مع تعديل معرف الطالب يدوياً.
- ولي واحد يرى أبناءه الموثقين فقط عبر مدارس مختلفة.
- الطالب الذي له وليان يظهر لكل منهما وفق حالة الرابط وصلاحياته.
- فك رابط ولي لا يحذف سجل الطالب ولا يؤثر على رابط ولي آخر.
- OTP منتهٍ أو خاطئ أو مستهلك أو بعد تجاوز المحاولات يُرفض.
- رقم حساب موجود وغير موجود وموقوف لا يكشف اختلافاً في رد طلب OTP.
- تحديد المعدل يعمل عبر عدة نسخ للخادم وإعادة تشغيله.
- إيقاف الحساب وتغيير كلمة المرور يبطلان الجلسات وفق سلوك موثق ومختبر.
- لا كلمات مرور أو OTP أو أسرار في قاعدة البيانات أو السجلات أو APK.
- انقطاع الشبكة لا يعرض بيانات قديمة كأنها حديثة ولا يكرر العمليات عند عودة الاتصال.

## 9. بوابات الموافقة
هذه الوثيقة لا تمنح إذناً لتطبيق migrations على الإنتاج أو حذف/تعديل بيانات حية أو تغيير إعدادات Auth أو ربط مزود SMS. كل ذلك يحتاج موافقة مستقلة بعد عرض التغييرات الدقيقة وخطة الرجوع ونتائج staging.

**المطلوب من التنفيذ:** مراجعة FIX-1 وAPP-2 والمخطط الفعلي، إعداد migrations وRLS وRPC على بيئة تطوير فقط، ثم تقديم diff ونتائج اختبارات قابلة للتحقق. لا يبدأ التطبيق على الإنتاج.
